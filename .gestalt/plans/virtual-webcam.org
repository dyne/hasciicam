* TODO [#A] Fix the product scope and frame contract
:PROPERTIES:
:Effort: 0.5 day
:Goal: Define exactly what HasciiCam publishes, when the virtual camera exists, and which platform versions are supported before adding platform code.
:Notes: Challenge the first idea of capturing the final SDL window: that would include the cursor, ImGui overlay, letterboxing, and possibly OS scaling, and would require a slow GPU readback. The SDL driver already maintains `stream_pixels`, a CPU ARGB8888 image containing only the rendered ASCII cells. Publish that buffer immediately after glyph rasterization and before the cursor, GUI overlay, and `SDL_RenderPresent()`. This keeps the webcam image stable and prevents private controls from appearing in calls. Use the modern `MFCreateVirtualCamera` path for the first Windows implementation. Microsoft documents Windows build 22000 as the minimum, so Windows 11 is the explicit first target; do not silently claim Windows 10 support. A Windows 10 DirectShow virtual-camera filter or signed camera driver is a separate product and packaging effort. Reference: https://learn.microsoft.com/en-us/windows/win32/api/mfvirtualcamera/nf-mfvirtualcamera-mfcreatevirtualcamera and https://github.com/microsoft/Windows-Camera/tree/master/Samples/VirtualCamera. Linux relies on an externally installed and loaded `v4l2loopback` kernel module; HasciiCam is a frame producer, not a kernel-module installer. Reference: https://github.com/v4l2loopback/v4l2loopback.
:END:
